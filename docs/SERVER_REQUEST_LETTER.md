- **받는 사람**: edu-manager-api 운영 담당자
- **작성일**: 2026-09-11
- **첨부**: `SERVER_CHANGE_SPEC.md` (상세 기술 스펙)

안녕하세요.

학원 입구에 설치할 **얼굴인식 출석 단말**을 edu-manager-api 와 연동하는 작업을 진행하고 있습니다.

저희도 처음에는 **이미 있는 API(로그인·학생·수업·출석)만으로 충분히 가능할 것**이라고 생각하고 시작했습니다.
실제로 확인해 보니 **대부분은 정말 기존 API만으로 해결됐고**, 딱 한 가지에서만 막혔습니다.

그 한 가지가 왜 막히는지, 그리고 어떤 선택지가 있는지를 정리해서 공유드립니다.
먼저 결론부터 요약하면 다음과 같습니다.

| | 필요한 기능 | 기존 API로 가능한가 |
|---|---|---|
| 1 | 얼굴로 사람 판별 | ✅ 단말에서 처리 (API 불필요) |
| 2 | 오늘 이 학생 수업이 있는지 확인 | ✅ **가능** — `GET /api/v1/attendance/today` |
| 3 | "출석하시겠습니까?" 버튼 표시 | ✅ 단말에서 처리 (API 불필요) |
| 4 | **출석 + 출석 시각 기록** | ⚠️ **여기만 막힘** |
| 5 | 이미 출석한 사람은 안 묻기 | ✅ **가능** — 위 응답의 `checkedInAt` |

즉 **5개 중 4개는 기존 API로 이미 동작을 확인**했습니다. 아래는 4번에 대한 설명입니다.

---

## 1. 기존 API로 확인된 것 (잘 되고 있습니다)

먼저 잘 된 부분부터 말씀드립니다. 아래는 모두 실제로 호출해서 확인했습니다.

**로그인 → 토큰 발급 → 조직 헤더 → 데이터 조회**까지 전부 정상입니다.

`GET /api/v1/attendance/today` 한 번만 호출하면 이런 응답이 옵니다.

```json
{
  "date": "2026-09-11", "weekday": 5,
  "expectedCount": 7, "checkedInCount": 0, "notYetCount": 7,
  "rows": [
    {
      "enrollmentId": "11111111-1111-4111-8111-111111111111",
      "studentId": "22222222-2222-4222-8222-222222222222",
      "name": "학생A", "subject": "인공지능 웹 개발", "teacher": "강사A",
      "startTime": "14:00", "durationMinutes": 100,
      "checkedInAt": null, "source": null
    }
  ]
}
```

이 응답 하나로 **2번과 5번이 동시에 해결**됩니다.

- 인식한 이름이 `rows` 에 있으면 → **오늘 수업이 있는 학생**
- 그 행의 `checkedInAt` 에 값이 있으면 → **이미 출석함, 버튼을 띄우지 않음**

이 부분은 추가 작업이 전혀 필요 없습니다. 잘 만들어 주셔서 감사합니다.

## 2. 막힌 부분 — "출석 시각"을 저장할 자리가 없습니다

문제는 4번, **출석을 기록하는 쪽**입니다.

기존 API 중 출석을 기록하는 것은 이것입니다.

```
PUT /api/v1/monthly-enrollments/{id}/attendances/{date}
본문: { "value": "O" }
```

이걸 쓰면 출석 체크 자체는 됩니다. 그런데 저장된 데이터를 조회해 보니 구조가 이랬습니다.

```json
"attendance": { "2": "O" }
```

**`날짜(일) → "O"` 문자열 하나**입니다. 실제 9월 데이터 34행 중 10행에 값이 들어있는데 모두 같은 형태였습니다.

즉 이 구조에는 **"몇 시 몇 분에 왔는지"를 넣을 자리가 물리적으로 없습니다.**
`"O"` 대신 `"14:03"` 을 억지로 넣으면 기존 출석부 화면과 집계가 깨질 것이고,
그렇다고 시각을 포기하면 **"출석 시각도 함께 기록한다"는 요구사항 자체가 성립하지 않습니다.**

정리하면 기존 API 방식의 한계는 이렇습니다.

| 항목 | `PUT monthly-enrollments` 방식 |
|---|---|
| 출석 O/X 표시 | ✅ 가능 |
| **출석 시각 기록** | ❌ **저장할 필드가 없음** |
| 얼굴인식/수동 구분 | ❌ 구분 불가 |
| 중복 전송 방지 | ❌ 없음 (네트워크 재시도 시 중복 위험) |
| 단말이 가져야 할 권한 | ⚠️ **관리자 로그인 계정** |

마지막 항목도 말씀드리고 싶습니다.
이 방식으로 가려면 **현관에 놓인 단말기 안에 관리자 아이디·비밀번호를 저장**해야 합니다.
그 단말은 학원 입구에 상시 켜져 있는 기기인데, 만약 분실되거나 접근당하면
**학원 전체 학생 정보와 수업·수납 정보를 읽고 고칠 수 있는 계정**이 함께 넘어갑니다.
출석 한 줄 기록하자고 지불하기에는 조금 큰 위험이라고 생각합니다.

## 3. 그런데 서버에 이미 그 기능이 들어가 있습니다

여기서 저희도 예상 못 한 것을 발견했습니다.

API 가이드 문서에 `POST /internal/face/check-ins` 라는 **얼굴인식 전용 출석 엔드포인트**가 설명돼 있어서
시험 삼아 호출해 봤는데, 이런 응답이 왔습니다.

```
503  { "error": { "code": "NOT_CONFIGURED",
                  "message": "얼굴인식 등원 웹훅이 설정되지 않았습니다." } }
```

**한국어로 된 전용 에러 메시지**가 돌아온다는 것은, 그 주소가 존재하지 않는 게 아니라
**이미 서버에 배포되어 있고 다만 "설정이 안 됐다"고 스스로 알려주는 상태**라는 뜻입니다.
(주소가 없으면 `404 Not Found` 가 옵니다.)

그리고 이 엔드포인트는 앞의 한계를 정확히 메우도록 설계돼 있습니다.

| 항목 | `/internal/face/check-ins` |
|---|---|
| 출석 O/X 표시 | ✅ |
| **출석 시각 기록** | ✅ `checked_in_at` 필드 |
| 얼굴인식/수동 구분 | ✅ `source: "face"` |
| 중복 전송 방지 | ✅ `idempotency_key` |
| 단말이 가져야 할 권한 | ✅ **서명용 키 하나뿐** (출석 기록만 가능) |

실제로 `attendance/today` 응답에 `checkedInAt` 과 `source` 필드가 이미 준비돼 있는 것도
이 엔드포인트가 채워 넣을 자리로 보입니다.

**그래서 저희가 드리는 요청은 "새 기능을 만들어 달라"가 아니라,
"이미 들어가 있는 기능을 켜 달라"에 가깝습니다.** 다만 한 군데만 실제 데이터와 맞지 않아
작은 수정이 필요합니다.

## 요청 1. 웹훅을 켜 주세요 (설정 확인)

위 `503 NOT_CONFIGURED` 를 없애는 일입니다.
확인차 **일부러 틀린 키로 서명해서 보내도 똑같이 503**이 나옵니다.
서명을 검사하는 단계까지 가지도 못하고 그 앞에서 멈춘다는 뜻이라,
서버가 서명용 키 값을 읽지 못하고 있는 상태로 보입니다.

확인 부탁드릴 세 가지입니다.

1. Vercel 프로젝트 환경변수에 `FACE_CHECKIN_WEBHOOK_SECRET` 이 등록돼 있고 **Production 스코프**가 포함돼 있는지
2. 환경변수를 추가한 뒤 **재배포(Redeploy)** 를 했는지 — Vercel 은 재배포해야 새 환경변수가 반영됩니다
3. 조직(org) 단위로 이 기능을 켜는 설정이 따로 있다면, 해당 조직에 활성화돼 있는지

> 가이드 문서상 `NOT_CONFIGURED` 는 "서명 키 **또는** 조직이 설정되지 않음" 을 뜻한다고 되어 있어 두 가지를 모두 적었습니다.

이것만 해결되면 서명 방식이 맞는지 저희 쪽에서 바로 검증할 수 있습니다.

## 요청 2. 웹훅이 `student_id` 로도 학생을 찾게 해 주세요 (소스 수정)

### 왜 필요한가

현재 이 웹훅은 `attendance_no`(출석번호)로 학생을 찾도록 되어 있습니다.
그런데 실제 데이터를 조회해 보니 그 값이 거의 비어 있었습니다. (2026-09-11 기준)

| 항목 | 값 |
|---|---|
| 전체 학생 | 45명 |
| `attendance_no` 가 있는 학생 | **7명** |
| `legacy_code` 가 있는 학생 | 35명 |
| **오늘 수업이 있는 7명 중 `attendance_no` 보유** | **0명** |

```
이름       attendance_no   legacy_code
학생A      None            None
학생B      None            90002
학생C      None            90003
학생D      None            90004
학생E      None            None
학생F      None            90006
학생G      None            90007
```

그래서 요청 1을 해결하더라도, 지금 상태로는 **오늘 출석 대상 전원이
`404 UNKNOWN_STUDENT`(그런 학생 없음)** 로 실패합니다.
`legacy_code` 를 대신 쓰는 방법도 검토했지만 7명 중 2명(학생A·학생E)은 그것도 비어 있어
완전한 해결이 되지 않았습니다.

물론 **학생 45명의 출석번호를 전부 채워 넣는 방법**도 있습니다.
다만 그렇게 하면 앞으로 신규 학생이 등록될 때마다 계속 같은 관리를 해야 해서,
언젠가 한 명이 누락되면 그 학생만 조용히 출석이 안 되는 일이 생길 것 같습니다.

### 제안하는 방법

앞서 보신 `attendance/today` 응답에는 **이미 `studentId`(UUID)가 들어 있습니다.**

```json
{ "studentId": "22222222-2222-4222-8222-222222222222", "name": "학생A", ... }
```

단말은 **명단을 받을 때 같이 온 이 값을 그대로 되돌려주기만** 하면 됩니다.
따로 입력할 데이터가 없고, 신규 학생도 등록되는 순간 자동으로 동작합니다.

그래서 웹훅 요청 본문에 `student_id` 를 받아주시기를 요청드립니다.

```json
{
  "version": 1,
  "device_id": "jetson-01",
  "student_id": "22222222-2222-4222-8222-222222222222",
  "checked_in_on": "2026-09-11",
  "checked_in_at": "14:03:21",
  "idempotency_key": "jetson-01:4f7bb96f-…:2026-09-11"
}
```

| 필드 | 요청 내용 |
|---|---|
| `student_id` | **신규 추가** — 학생 UUID (`students.id`), 선택 필드 |
| `attendance_no` | 기존 유지하되 **선택 필드로 완화** |
| 그 외 | 변경 없음 |

- 두 값 중 **최소 하나**가 있으면 통과, 둘 다 없으면 `400 INVALID_PAYLOAD`
- 학생 조회 순서: `student_id` → 없으면 `attendance_no` → 둘 다 실패 시 `404 UNKNOWN_STUDENT`
- **서명 검증, 중복 처리(`200 duplicate`), `source: "face"` 기록, `checked_in_at` 저장은 기존 그대로**

기존 동작을 바꾸는 게 아니라 **찾는 방법을 하나 더 허용**하는 것이라,
이미 `attendance_no` 로 연동 중인 곳이 있어도 영향이 없습니다.

가능하시면 응답에도 `student_id` 를 포함해 주시면 단말에서 결과를 대조하기가 수월합니다.

```json
{ "data": { "check_in_id": "...", "student_id": "...",
            "student_name": "학생A", "outcome": "recorded" } }
```

### 참고

`/internal/*` 은 `X-Organization-Id` 헤더를 쓰지 않으므로, 서버가 `device_id` 나 서명 키로
조직을 판별해야 합니다. 지금처럼 단일 조직(`00000000-0000-4000-a000-000000000001`) 운영이면
그대로 두셔도 되고, 나중에 여러 학원을 지원하실 계획이라면 `device_id → org_id` 매핑이 필요해 보입니다.

## 만약 서버 수정이 어렵다면

요청 2가 부담스러우시면 **기존 `PUT monthly-enrollments` 방식으로도 진행은 가능합니다.**
다만 그 경우 아래를 서로 합의해 두어야 할 것 같습니다.

- 서버에는 **출석 여부(`"O"`)만 남고, 출석 시각은 단말에만 저장**됩니다
- 나중에 "누가 몇 시에 왔는지"를 관리자 화면에서 보려면 그때 다시 서버 작업이 필요합니다
- 단말에 관리자 로그인 계정을 저장해야 하는 보안 부담이 남습니다

저희는 **요청 1 + 요청 2** 쪽을 권해드리지만, 판단은 맡기겠습니다.

정리하면 —
**기존 API 덕분에 5단계 중 4단계는 이미 해결됐고**, 남은 것은 "출석 시각을 어디에 저장하느냐" 하나입니다.
그리고 그걸 위한 엔드포인트는 이미 서버에 들어가 있어서, **켜는 것 + 학생을 찾는 방법 하나 추가**면 될 것 같습니다.
